Summary

Built the Ubuntu Server VM that would host the Wazuh manager, installed the OS, and brought up the full Wazuh all-in-one stack — manager, indexer, and dashboard — ending with a working login to the web console.

The constraint

The VM needed to be sized for a genuinely heavy workload. Wazuh's all-in-one deployment bundles an indexer (Elasticsearch/OpenSearch-based), the manager itself, and a dashboard — all running on one guest, with no spare capacity to recover from an undersized disk or memory allocation mid-install.

The fix
Created a new VM in Proxmox: 2 vCPU, 4 GB RAM, 40 GB disk, network on vmbr1 (SOC VLAN, 172.16.30.0/24).
Installed Ubuntu Server 24.04 LTS, enabling OpenSSH during setup for remote access from the start rather than configuring it after the fact.
Downloaded Wazuh's official all-in-one installer and ran it:
bash
  sudo bash ./wazuh-install.sh -a
Confirmed all core services came up cleanly: wazuh-manager, wazuh-indexer, wazuh-dashboard, and filebeat.
Accessed the Wazuh dashboard from a browser at https://172.16.x.x, logging in with the admin credentials generated by the installer.
Outcome

The Wazuh manager and dashboard are installed and reachable — logs can now be forwarded to this VM and viewed through the web console going forward.

Key takeaway

For log-indexing stacks like Wazuh, disk and memory sizing isn't something to approximate — the indexer component in particular has real headroom requirements that are easy to underestimate when scoping a VM for "just a manager.
